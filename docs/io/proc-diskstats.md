# Understanding /proc/diskstats

> Every field explained, with kernel sources and practical analysis patterns

## What is /proc/diskstats?

`/proc/diskstats` is the kernel's per-block-device I/O accounting table. It is generated by [`diskstats_show()`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/block/genhd.c) in `block/genhd.c`, which walks every registered disk and partition and emits a snapshot of their [`struct disk_stats`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/include/linux/blkdev.h) counters.

Every I/O that passes through the block layer updates these counters via `blk_account_io_start()` and `blk_account_io_done()`. The counters are maintained per-CPU and merged on read to avoid contention.

```bash
$ cat /proc/diskstats
 8   0 sda    12345  678  901234  56789  98765  4321  876543  21098  0  12345  77887  0  0  0  0  0  0
 8   1 sda1    9876  123  750000  40000  80000  1000  700000  15000  0   9000  55000  0  0  0  0
 8   2 sda2    2000   50  120000  10000  12000   200  120000   4000  0   2100  14000  0  0  0  0
 253  0 dm-0   11000  0   870000  60000  95000     0  820000  24000  0  11500  84000  0  0  0  0  0  0
259  0 nvme0n1 50000 3000 8000000 25000 200000 15000 6000000  18000  0  15000  43000 1000  0 2000000 500 200 300
```

### Field layout

The three leftmost columns are device identity; the remaining columns are I/O statistics:

```
MAJ  MIN  NAME  [fields 1-11, plus fields 12-15 and 16-17 on newer kernels]
```

| Column | Meaning |
|--------|---------|
| `MAJ` | Major device number |
| `MIN` | Minor device number |
| `NAME` | Device name as registered in the block layer |
| Fields 1–11 | Present since kernel 2.6.x |
| Fields 12–15 | Discard statistics, added in Linux 4.18 |
| Fields 16–17 | Flush statistics, added in Linux 5.5 |

## The Fields

### Fields 1–4: Read statistics

**Field 1 — reads completed successfully**

Total number of reads that were issued to the device and completed. This is a monotonically increasing counter since boot (or since the device was registered).

- Incremented in `blk_account_io_done()` for read requests.
- Use deltas over time to get read IOPS: `Δreads_completed / Δt`.

**Field 2 — reads merged**

Number of read requests that the I/O scheduler merged with an adjacent request before submission to the driver. When two reads target consecutive sectors, they can be merged into a single larger bio.

- Front merge: the new request's end sector aligns with an existing request's start sector.
- Back merge: the new request's start sector aligns with an existing request's end sector.
- Incremented in `blk_attempt_req_merge()` in `block/blk-merge.c`.

High merge counts indicate sequential read access. Zero merges on a device receiving heavy reads suggests either purely random I/O or an NVMe device (NVMe's queue model largely bypasses the legacy merge path).

**Field 3 — sectors read**

Total 512-byte sectors successfully read. Multiply by 512 to get bytes.

- To get read throughput: `Δsectors_read * 512 / Δt`.
- Note: the kernel always uses 512-byte logical sectors in this counter regardless of the physical sector size of the underlying device.

**Field 4 — time spent reading (ms)**

Cumulative wall-clock milliseconds spent on read I/O, measured from when a read bio enters `blk_account_io_start()` until it completes in `blk_account_io_done()`. This is summed over all read requests.

- Use to calculate average read latency: `Δtime_reading / Δreads_completed` (in ms/IO).
- Elevated values relative to IOPS indicate latency spikes, not just throughput issues.

### Fields 5–8: Write statistics

**Field 5 — writes completed**

Total writes issued and completed. The write equivalent of field 1.

- Use deltas for write IOPS: `Δwrites_completed / Δt`.

**Field 6 — writes merged**

Writes merged by the I/O scheduler. Same mechanics as field 2.

High `writes_merged / writes_completed` ratio → sequential writes (good for HDDs, irrelevant for NVMe). Low ratio → random writes (problematic for HDDs, fine for NVMe).

**Field 7 — sectors written**

Total 512-byte sectors successfully written.

- Write throughput: `Δsectors_written * 512 / Δt`.

**Field 8 — time spent writing (ms)**

Cumulative milliseconds spent on write I/O. Same semantics as field 4 but for writes.

- Average write latency: `Δtime_writing / Δwrites_completed`.
- Separating read and write latency is critical: many SSDs exhibit asymmetric read/write latency profiles, especially under mixed workloads.

### Fields 9–11: In-flight and I/O time

**Field 9 — I/Os currently in flight**

Number of I/O requests currently in the block layer — submitted to the device driver but not yet completed. This is a **snapshot value**, not a cumulative counter. It can go up and down.

- Maintained as a per-CPU counter via `disk_stats.in_flight[]`.
- Reads in flight use index 0, writes use index 1.
- The exported value is the sum.

A sustained nonzero value means the device has a backlog. For an NVMe with a deep hardware queue, this is normal and desirable. For a traditional HDD, sustained high values indicate saturation.

**Field 10 — time spent doing I/Os (ms)**

Cumulative milliseconds during which the device had at least one request in flight. This measures "disk busy time" — how long the device was not idle.

- Incremented in units of jiffies converted to milliseconds, via `part_stat_add()` on the `io_ticks` field.
- Use to calculate device utilization over an interval:

```
util% = (Δtime_io / Δwall_time_ms) * 100
```

At 100% utilization the device was busy for the entire measurement window. For traditional HDDs this is a hard ceiling. For SSDs and NVMe with internal parallelism, sustained 100% does not necessarily mean saturation — look at latency and queue depth too.

**Field 11 — weighted time spent doing I/Os (ms)**

The sum of (time each individual request spent in flight multiplied by the number of in-flight requests at that moment), accumulated across all requests. Also known as the **I/O service time weighted by queue depth**.

This is the correct input for computing average queue depth:

```
avg_queue_depth = Δweighted_time / Δwall_time_ms / 1000
```

The division by 1000 converts milliseconds of queue-depth-seconds into the dimensionless average queue depth (requests per unit time).

- Low `avg_queue_depth` (< 1) → device is mostly idle between requests, I/O is not queued.
- For NVMe, a healthy queue depth for throughput is 8–32. If `avg_queue_depth` is 1–2 on an NVMe, throughput is likely limited by submission rate, not device capacity.

### Fields 12–15: Discard statistics (Linux 4.18+)

Added by [commit 9e234eea9c00](https://git.kernel.org/linus/9e234eea9c00) in Linux 4.18. Discard requests tell the device (typically an SSD) that a range of LBA space is no longer in use and can be erased or returned to the free pool. They are generated by `fstrim`, filesystem discard mount options, and LVM thin provisioning.

**Field 12 — discards completed**

Total DISCARD requests completed.

**Field 13 — discards merged**

DISCARD requests merged before submission. Merging adjacent discard ranges reduces command overhead.

**Field 14 — sectors discarded**

Total 512-byte sectors covered by completed discard operations.

**Field 15 — time spent discarding (ms)**

Cumulative milliseconds spent processing DISCARD requests.

- Heavy discard activity can compete with foreground I/O on some SSDs. Monitor with `Δtime_discarding / Δdiscards_completed` for per-discard latency.
- If `discards_completed` is zero, either the device does not support TRIM/DISCARD or the filesystem is not issuing them.

### Fields 16–17: Flush statistics (Linux 5.5+)

Added by [commit f3fa33acca9f](https://git.kernel.org/linus/f3fa33acca9f) in Linux 5.5. Flush requests (FLUSH/FUA) force the device's write cache to persistent storage.

**Field 16 — flush requests completed**

Total flush commands (cache flush / FUA write) completed. Incremented once per flush bio, not once per fsync — one fsync typically issues one flush, but a single flush can cover many pending writes.

**Field 17 — time spent flushing (ms)**

Cumulative milliseconds spent completing flush requests.

- High `time_flushing / flushes_completed` (e.g., > 5 ms per flush) on a device that advertises write cache indicates a slow flush path — the device may be flushing more aggressively than necessary.
- If `flushes_completed` is zero with `fsync`-heavy workloads, the device has either disabled write cache or is using FUA writes on individual commands rather than explicit flush commands.

## Kernel Implementation

### struct disk_stats

```c
/* include/linux/blkdev.h */
struct disk_stats {
    u64 nsecs[NR_STAT_GROUPS];       /* time in nanoseconds per I/O group */
    unsigned long sectors[NR_STAT_GROUPS];
    unsigned long ios[NR_STAT_GROUPS];
    unsigned long merges[NR_STAT_GROUPS];
    unsigned long io_ticks;          /* total time with at least one I/O in flight */
    local_t in_flight[2];            /* reads [0] and writes [1] currently in flight */
};
```

`NR_STAT_GROUPS` is defined as 4 in `include/linux/blkdev.h`, covering reads, writes, discards, and flushes (in that index order).

Each field is maintained per-CPU to avoid cache line contention. When `/proc/diskstats` is read, `part_stat_read_all()` aggregates across CPUs.

### blk_account_io_start()

```c
/* block/blk-core.c (simplified) */
void blk_account_io_start(struct request *rq)
{
    struct disk_stats *stats = &rq->rq_disk->part0.dkstats;
    int rw = op_stat_group(req_op(rq));  /* maps op to stat group index */

    /* Increment in-flight count */
    part_stat_local_inc(stats, in_flight[rw == STAT_WRITE]);

    /* Record start time for latency accounting */
    rq->start_time_ns = ktime_get_ns();
}
```

### blk_account_io_done()

```c
/* block/blk-core.c (simplified) */
void blk_account_io_done(struct request *rq, u64 now)
{
    struct disk_stats *stats = &rq->rq_disk->part0.dkstats;
    int rw = op_stat_group(req_op(rq));
    u64 duration = now - rq->start_time_ns;

    /* Decrement in-flight, increment completed and time */
    part_stat_local_dec(stats, in_flight[rw == STAT_WRITE]);
    part_stat_inc(stats, ios[rw]);
    part_stat_add(stats, sectors[rw], blk_rq_sectors(rq));
    part_stat_add(stats, nsecs[rw], duration);

    /* Update io_ticks and weighted time */
    update_io_ticks(stats, jiffies, true);
}
```

`update_io_ticks()` adds the elapsed time since the last tick update to `io_ticks` if any requests were in flight during that window. It also accumulates the weighted time used for queue depth calculation.

### diskstats_show()

```c
/* block/genhd.c (simplified) */
static int diskstats_show(struct seq_file *seqf, void *v)
{
    struct gendisk *gp = v;
    struct disk_part_iter piter;
    struct block_device *hd;

    disk_part_iter_init(&piter, gp, DISK_PITER_INCL_EMPTY_PART0);
    while ((hd = disk_part_iter_next(&piter))) {
        struct disk_stats stat;
        part_stat_read_all(hd, &stat);

        seq_printf(seqf,
            "%4d %7d %s "
            "%lu %lu %lu %u "   /* reads: ios merges sectors ms */
            "%lu %lu %lu %u "   /* writes: ios merges sectors ms */
            "%u %u %u "         /* in_flight io_ticks weighted */
            "%lu %lu %lu %u "   /* discards: ios merges sectors ms */
            "%lu %u\n",         /* flushes: ios ms */
            ...);
    }
    disk_part_iter_exit(&piter);
    return 0;
}
```

### Per-CPU aggregation

Stats are updated with `part_stat_add()` / `part_stat_inc()`, which are thin wrappers around `__this_cpu_add()`. At read time, `part_stat_read_all()` calls `for_each_possible_cpu()` and sums the per-CPU structures. This means:

1. There is no lock held during the read — the snapshot is not strictly atomic across all fields.
2. On a system with many CPUs, the read-time aggregation cost is proportional to CPU count.
3. The `in_flight` field uses `local_t` (not atomic_t) for lock-free fast-path updates.

## iostat: the Userspace Interface

`iostat` (from the `sysstat` package) is the standard tool for reading `/proc/diskstats`. It reads the file, waits an interval, reads again, and computes rates from the deltas.

```bash
# Extended stats, 1-second intervals, skip idle devices
iostat -xz 1

# Specific device, extended stats
iostat -d nvme0n1 -x 1

# Human-readable units (MB/s instead of kB/s)
iostat -xz -h 1

# Show timestamps
iostat -xz -t 1
```

### Mapping iostat columns to /proc/diskstats fields

| iostat column | Formula from diskstats | Notes |
|--------------|----------------------|-------|
| `r/s` | `Δreads_completed / Δt` | Read IOPS |
| `w/s` | `Δwrites_completed / Δt` | Write IOPS |
| `d/s` | `Δdiscards_completed / Δt` | Discard IOPS (sysstat ≥ 12.0) |
| `f/s` | `Δflushes_completed / Δt` | Flush IOPS (sysstat ≥ 12.0) |
| `rkB/s` | `Δsectors_read * 512 / Δt / 1024` | Read throughput in kB/s |
| `wkB/s` | `Δsectors_written * 512 / Δt / 1024` | Write throughput in kB/s |
| `rrqm/s` | `Δreads_merged / Δt` | Read merge rate |
| `wrqm/s` | `Δwrites_merged / Δt` | Write merge rate |
| `r_await` | `Δtime_reading / Δreads_completed` | Average read latency (ms) |
| `w_await` | `Δtime_writing / Δwrites_completed` | Average write latency (ms) |
| `await` | `(Δtime_reading + Δtime_writing) / (Δreads + Δwrites)` | Combined average latency (ms) |
| `%util` | `Δtime_io / Δwall_ms * 100` | Device utilization |
| `aqu-sz` | `Δweighted_time / Δwall_ms / 1000` | Average queue depth |
| `svctm` | Deprecated — do not use | Was an estimate of service time, removed in newer sysstat |

**`await` vs `svctm`**: `await` includes time waiting in the OS queue before the request reached the device. `svctm` attempted to subtract queue wait time, but the estimation was unreliable and has been removed. For modern storage, latency at the application level is what matters; `await` captures this correctly.

## Common Analysis Patterns

### Detecting device saturation

```bash
# Print device name, util%, and await when util > 80%
iostat -xz 1 | awk '
  /^Device/ { hdr=1; next }
  hdr && NF > 1 {
    util = $NF
    await = $(NF-4)   # position varies by sysstat version; use -x output
    if (util+0 > 80)
      printf "SATURATED: %-12s util=%.1f%% await=%.2fms\n", $1, util, await
  }
'
```

For HDDs: `%util` approaching 100% is a hard saturation signal. Service time cannot improve further.

For NVMe: `%util` can reach 100% while latency is still acceptable because the device has deep internal parallelism. Look at `aqu-sz` and `r_await`/`w_await` instead:

```bash
# NVMe saturation heuristic: high queue depth AND rising latency
iostat -xz 1 nvme0n1 | awk 'NR>3 { print "qd="$NF-4, "await="$10 }'
```

### Read vs write split

The separate read/write counters (fields 1–8) allow detailed direction-specific analysis:

```bash
# Print read/write IOPS and latency breakdown
iostat -x 1 | awk 'NR>3 && $1 ~ /^(sd|nvme|vd)/ {
  printf "%s  r/s=%-8s w/s=%-8s r_await=%-8s w_await=%s\n",
         $1, $4, $5, $11, $12
}'
```

High `w_await` relative to `r_await` is common on SSDs under write pressure (write amplification, garbage collection). The inverse (slow reads, fast writes) is unusual and may indicate a read caching problem.

### Diagnosing merge efficiency

```bash
# Merge ratio: what fraction of I/Os were merged before submission
awk '
/^[[:space:]]*8/ {                     # sda (major 8)
  reads=$4; rmerges=$5
  writes=$8; wmerges=$9
  if (reads+rmerges > 0)
    printf "read  merge ratio: %.1f%%\n", rmerges/(reads+rmerges)*100
  if (writes+wmerges > 0)
    printf "write merge ratio: %.1f%%\n", wmerges/(writes+wmerges)*100
}' /proc/diskstats
```

| Merge ratio | Interpretation |
|-------------|---------------|
| > 50% | Highly sequential access — good for rotational media |
| 10–50% | Mixed sequential and random |
| < 5% | Mostly random, or NVMe/device bypassing scheduler |
| Exactly 0 | `mq-deadline` or `none` scheduler, or NVMe |

### Computing average queue depth from raw /proc/diskstats

```bash
# Snapshot delta to compute average queue depth over a 1-second window
read_diskstats() { awk -v dev="$1" '$3==dev {print $12, $13}' /proc/diskstats; }

dev=sda
read1=$(read_diskstats $dev); t1=$(date +%s%3N)
sleep 1
read2=$(read_diskstats $dev); t2=$(date +%s%3N)

awk -v r1="$read1" -v r2="$read2" -v dt="$((t2-t1))" '
BEGIN {
  split(r1, a); split(r2, b)
  delta_weighted = b[2] - a[2]   # field 11 (weighted time, ms)
  aqu = delta_weighted / dt
  printf "avg_queue_depth = %.2f\n", aqu
}'
```

### Watching discard activity during fstrim

```bash
# Before trim
before=$(awk '/sda / {print $13, $14, $15, $16}' /proc/diskstats)

# Run trim
fstrim -v /

# After trim
after=$(awk '/sda / {print $13, $14, $15, $16}' /proc/diskstats)

echo "before: $before"
echo "after:  $after"
# field 12: discards completed, field 14: sectors discarded
```

### Flush/fsync overhead

```bash
# Estimate flush overhead as fraction of total I/O time
awk '/nvme0n1 / {
  total_time = $11   # field 10: time doing I/Os
  flush_time = $18   # field 17: time flushing
  if (total_time > 0)
    printf "flush overhead: %.1f%%\n", flush_time/total_time*100
}' /proc/diskstats
```

High flush overhead (> 20%) with sync-heavy workloads suggests examining fsync frequency or exploring `O_DSYNC` / barrier optimizations.

## /sys/block/device/stat

The same counters are also available per-device through sysfs:

```bash
cat /sys/block/nvme0n1/stat
# 50000 3000 8000000 25000 200000 15000 6000000 18000 0 15000 43000 1000 0 2000000 500 200 300
```

This is identical in format to the diskstats fields for that device (without the major/minor/name prefix). It is useful when scripting single-device monitoring without parsing a multi-device file:

```bash
# Poll a single device's stats without awk field extraction
watch -n 1 'cat /sys/block/nvme0n1/stat'
```

Partitions also have a stat file:

```bash
cat /sys/block/sda/sda1/stat
```

## Per-Partition Stats

`/proc/diskstats` contains entries for both whole disks and individual partitions. The behavior differs:

- **Whole disks** (`sda`, `nvme0n1`): all fields are populated, including in-flight (field 9), io_ticks (field 10), and weighted_time (field 11).
- **Partitions** (`sda1`, `nvme0n1p1`): reads, writes, and sectors are tracked per-partition. The in-flight and time fields may be zero or absent for partitions on older kernels, as partition-level time accounting was not always maintained.

For partition I/O analysis, use whole-disk fields 9–11 for latency and utilization. Use per-partition fields 1–8 to understand how I/O is split across partitions.

## Merges: Mechanics and Meaning

The I/O scheduler (now `blk-mq` schedulers: `mq-deadline`, `bfq`, `kyber`, or `none`) maintains a sorted queue of pending requests. When a new request arrives, the merge path in `block/blk-merge.c` checks for adjacent requests:

```
Front merge:  [existing_start ... existing_end] <- [new_start == existing_end]
Back merge:   [new_end == existing_start] -> [existing_start ... existing_end]
```

Both cases increment the `merges` counter for the respective direction. The merged request is larger and amortizes the per-request overhead (queue insertion, device command, completion interrupt).

**When merges happen**:
- Sequential reads/writes by a single process (e.g., `dd`, large file reads).
- Concurrent processes reading/writing adjacent file data (e.g., multi-threaded file copy).
- Read-ahead generating adjacent read requests.

**When merges do not happen**:
- Random I/O access patterns.
- NVMe with `none` or `mq-deadline` scheduler — the hardware can handle deep queues natively and merging adds latency without benefit.
- Very fast devices where the merge check overhead exceeds the benefit.
- `O_DIRECT` I/O that bypasses the page cache and issues requests individually.

For HDDs, high merge rates are a strong positive signal: they indicate the workload is behaving sequentially and making efficient use of disk bandwidth. For NVMe, zero merges is expected and not a concern.

## Diagnostic Patterns: Quick Reference

### Is my device saturated?

```bash
iostat -xz 1 | awk 'NR>3 && NF>1 && $NF+0 > 90 { print "BUSY:", $1, $NF"%" }'
```

### What is the current queue depth?

```bash
# Field 9 is a live snapshot of in-flight requests
awk 'NF>=12 { printf "%-15s in_flight=%s\n", $3, $10 }' /proc/diskstats
```

### Is write latency high relative to read?

```bash
iostat -x 1 5 | awk '/^sd|^nvme|^vd/ { print $1, "r_await="$11, "w_await="$12 }'
```

### Are discards slow?

```bash
# Compare discard time per sector to write time per sector
awk 'NF>=17 && $3=="sda" {
  ws = ($9>0) ? $9/$8 : 0      # write ms/sector (approx)
  ds = ($15>0) ? $16/$15 : 0   # discard ms/sector (approx; fields 14,15)
  printf "write ms/sector=%.4f  discard ms/sector=%.4f\n", ws, ds
}' /proc/diskstats
```

## Try It Yourself

```bash
# Print a one-line summary of each block device
awk 'NF>=12 {
  printf "%-10s reads=%-8s writes=%-8s in_flight=%s\n",
         $3, $4, $8, $10
}' /proc/diskstats

# Watch read/write IOPS changing in real time
watch -n 1 'awk "NF>=12 {printf \"%-12s r=%s w=%s\\n\", \$3, \$4, \$8}" /proc/diskstats'

# Compute 1-second IOPS deltas manually
prev=$(awk 'NF>=12 {print $3, $4, $8}' /proc/diskstats)
sleep 1
curr=$(awk 'NF>=12 {print $3, $4, $8}' /proc/diskstats)
paste <(echo "$prev") <(echo "$curr") | awk '{print $1, "r/s="$5-$2, "w/s="$6-$3}'

# Show devices with non-zero in-flight requests right now
awk 'NF>=12 && $10+0 > 0 { print $3, "in_flight="$10 }' /proc/diskstats
```
